# flow-start

Picks up one card and plans it (C2; Phases 1 and 2 of [architecture.md](../../../docs/architecture.md); D61). It ends when the user has approved the plan. Everything it does is remembered in `runs/<CARD-KEY>/`, saved to the card's branch of closio-agent (`runs/<CARD-KEY>`, never `main`; this folder itself stays on `main`), so it can be paused and continued: run it again and it carries on from the last finished step.

## Usage

- `/flow-start SCRUM-567`: pick up the card SCRUM-567 and plan it, or continue where it stopped.
- Codex: `$flow-start SCRUM-567` (approve the scripts outside the sandbox: git, GitLab over the VPN, pushes).

## Before every step: rules and user memory (rules A17, A7, A8; D62, D91)

For **each** numbered step below:

1. **The rules, read in full when the command starts (rule A17, D91):** at its start (also when it continues a card), read `AGENTS.md` and `docs/agent-rules.md` in full, then run `bash scripts/run.sh rules <KEY> read`. Read them again whenever the call in item 3 says they changed or that the conversation was summarized: say so in one line, read them, run `bash scripts/run.sh rules <KEY> read` again and go on (no stop to wait). Before each step, note the rules it touches (e.g. `A3`, `A12`, `A15`).
2. **Your memory, for every step:** the first step's is printed below when the command loads; every next step's is printed by the call in item 3 (`--memory pick-up <repos>`; from step 7 on: `--memory plan <repos>`), with the card's repos (`all` before you know them). Read the **user-created memory** entries it prints (the ones the user made with `flow-memory`, in `local/memory/`) and apply them. Team rules always win (A8): on a conflict, say so and follow the team rule.
3. **After every step, one call (D91):** `bash scripts/run.sh step <KEY> "pick-up <n>" "<what happened>" "rules: A3, A12 · memory: M2" --next <the next step> --memory <the next step's phase> <repos>` (use `—` when nothing applied). It writes the step in the card's history, moves to the next step (where a step below says "log the step; `set <KEY> step <n>`", this one call with `--next <n>` does both), checks whether the rules files changed since you read them (⚠️: read them again, item 1) and prints your memory for the next step. Where the phase changes at the end, use it without `--next` and run the `set` lines as written. Skip nothing.
4. **Ask and decide the grilling way (rule A26, D76; `rulesets/grilling.md`):** every question this command asks you, and every prompt you give during it that changes the card's plan, code, tests, data, Jira or GitLab: look up the facts first and show them as "Found" lines (never ask what the code or the files answer); ask only the real decisions, in numbered rounds, each with a recommended answer that "yes" accepts; follow-up rounds until nothing is open; sum up what was agreed and wait for the confirmation before changing anything; record them as item 5 says, with a one-line pointer in `card.md` (`## Decided before planning` for the planning questions). Short answers, approvals and the user's questions go straight through. The safety stops below stay their own plain yes/no.
5. **Every decision is recorded (rule A27, D77):** the moment a decision is confirmed (an answer to a question, an approval or a refusal at a stop, a memory entry that answered for the user, a change the user asked for), run `bash scripts/run.sh decide <KEY> "<step and its number>" "<question>" "<decided>" "<who / why>"` (who: `you`, `you: recommended`, `memory M2`); it prints the decision's number. Where this step keeps notes, write only a one-line pointer, e.g. `- Error code for a bad status: VALIDATION_ERROR (decision 3)`. A decision made before the card's folder exists (going on with a card that isn't To Do or is someone else's): record it right after `bash scripts/run.sh create`.

The first memory step runs here automatically:

!`bash scripts/memory.sh for pick-up all`

**If the block above still shows the command instead of its output** (e.g. in Codex), run `bash scripts/memory.sh for pick-up all` yourself first.

## Steps

**1. Start.** Run `bash scripts/run.sh check-folder`; if it fails, show the fix and stop. Read the card key typed after the command (in Claude Code it may also appear as `ARGUMENTS: …`); if it isn't like `SCRUM-567`, show the usage and stop. If `bash scripts/run.sh state <KEY>` shows a run folder, this is a continuation: run `bash scripts/run.sh branch <KEY>` first (it brings the card's run folder onto this Mac without switching this folder; ❌ = show the fix and stop), then read its `step:` line and **go straight to that step** (the steps before are done). **If that step is 8, 9 or 10 (planning), go to step 7 first:** the latest code is always read again before planning goes on (rule A18), and a draft plan is never saved before the approval, so it's made again. Then connect the VPN with the `flow-connectivity` agent (rule A5): GitLab is needed in step 5. If it fails, show its fix and stop.

**2. The card.** Read the card from Jira with your Jira tools (key, summary, issue type, status, assignee, sprint, description; the Jira API backup: `bash scripts/jira-api.sh get <KEY>`, see Rules). Read only here.
   - A **Spike**: say "the agent doesn't pick up Spikes" and stop (D58). Nothing is created.
   - Status **not To Do**, or **assigned to someone else**: say so and ask whether to go on. Stop until the user answers; on no, stop. (This one is asked on its own, before anything is created.)
   - Then: `bash scripts/run.sh branch <KEY>` (makes the card's branch of closio-agent ready without switching this folder; a teammate's run folder comes along if there is one), `bash scripts/run.sh create <KEY> "<summary>"`, and `bash scripts/run.sh set <KEY> type <issue type>`, `… set <KEY> jira_status <status>`.
   - Save the card's text to `runs/<KEY>/card.md` with your file-writing tool, exactly as Jira returns it (the same layout as `flow-check-card`: a title line, a `_Type · Status · Read on <date>_` line, then the description). Then run `bash scripts/card-check.sh runs/<KEY>/card.md` and show its output.
   - **The repos, worked out now** so they're asked in the same round as the card's gaps (D90): from the card's Scope section (and its title, e.g. "(WS2 + WS1)"), work out which registered repos the card needs (`config/repos/*.yaml`; the Scope sub-headings name them).
   - **One round for both (D90), the grilling way (item 4):** each ❌ of the card check (fix it in Jira, or explain it; a **Bug** may keep its gaps after the explanation, D58, so its recommended answer is to go on with them and what to explain), and the repos (recommended: the list you worked out; the user confirms, adds or removes). **Wait.** A gap fixed in Jira: read the card again and run the check again. Record each answer with `bash scripts/run.sh decide` (item 5), and write a one-line pointer for each explanation under a heading `## Explained at pick-up` at the end of `card.md`. Go on only when the user says so, and every ❌ is fixed or explained. No ❌: the round asks only about the repos.
   - Log the step; `bash scripts/run.sh set <KEY> step 3`.

**3. Jira.** With your Jira tools (these two changes are pre-approved, D57; never move a card to Blocked, A3; the Jira API backup: `sprint <KEY>`, `move <KEY> "In Development"`, `assign <KEY>`):
   - If the card isn't in the active sprint: find the active sprint (one issue from `project = SCRUM AND sprint in openSprints()` shows the Sprint field and its id) and set that sprint on the card (the Sprint field; on the first run, check the field's id on the card you read and note it in the history). If the sprint can't be set, say so with what you tried and go on; the user can move the card by hand (D13).
   - Move the card to **In Development** (if a tool needs the transition id, read the card's transitions first, read only).
   - Assign it to the user: the account ID is `JIRA_ACCOUNT_ID` in `local/user-settings.sh` (not a secret; if it's empty, say "run /flow-configure-user jira-account-id" and stop).
   - `bash scripts/run.sh set <KEY> jira_status "In Development"`; log the step; `set <KEY> step 4`.

**4. The repos.** The repos confirmed in step 2's round: `bash scripts/run.sh set <KEY> repos "<repo1>, <repo2>"`. When continuing a card whose repos weren't confirmed yet (its `repos:` line is empty), work them out as in step 2, show the list and ask the user to confirm, add or remove; wait. Log the step; `set <KEY> step 5`.

**5. The branches.** For each repo, in order:
   - **Folder access first (rule A15):** check this session can use the repo's folder (`local_path` in `local/repos/<repo>.yaml`): it's one of this session's folders, or reading a file in it works. If not, stop and ask the user to give access (Claude Code: `/add-dir <folder>` or a new session; Codex: start again with `codex --add-dir <folder>`), and go on only after they have.
   - The branch name: `bash scripts/branch-name.sh make <KEY> "<summary>"` suggests one (rule A12, at most 5 words, the same name in every repo). Show it and ask the user to confirm or change it (check a changed one with `bash scripts/branch-name.sh check <name>`); wait. Once, for all repos.
   - `bash scripts/card-branch.sh create <repo> <name>`: it fetches, pulls the repo's base branch (G1) and creates the branch, or reuses one that exists. Exit code 3 = uncommitted changes in that clone: **stop and ask** the user to commit or stash them, then run it again. ❌ = show the fix and stop. Never clone (D53); never run anything else in a repo here.
   - `bash scripts/run.sh set <KEY> branch <name>`; log the step with every repo's result; `set <KEY> step 6`.

**6. Save.** `bash scripts/run.sh set <KEY> phase plan`, `set <KEY> next "/flow-start <KEY>"` (the step lives only in the `step:` line), then `bash scripts/run.sh save <KEY> "picked up: In Development, branches created"`. Show its output. On ❌ (the push failed), show the fix and stop; the commit is kept.

**7. The code first (rule A18), never skipped.** Phase 2 starts here.
   - **The latest base branch:** for every repo, `bash scripts/card-branch.sh update <repo> <branch>`. Show its output. Exit code 3 = uncommitted changes in that clone: **stop and ask** the user to commit or stash them, then run it again. ❌ = show the fix and stop. ⚠️ (the branch has commits of its own) = go on, and also read the newer base code with the `git diff` it names.
   - **The ruleset (rule A19):** for every repo, `bash scripts/configure-repo.sh ruleset <repo>` and read the file it names (❌ = show the fix and stop): backend repos follow `rulesets/story-implementation-workflow.md`, the web app `rulesets/frontend-story-workflow.md`. It's read, never changed.
   - **The code:** in every repo the card needs, read the current code on the card's branch: routes, controllers, services, utils, constants, middlewares, migrations and seeders, and the WS1 locale files for messages (the ruleset's Step 3 lists the must-read files). Read what the card touches and its sibling modules. Never read or print `.env` values (A6). A plan is never made from the card alone.
   - Log the step with each repo's update result and the files you read; `set <KEY> step 8`.

**8. Questions first (rules A16, A18).** Compare the card with the code and list **every difference**, each with what the code has today and what the card says: error codes, HTTP statuses, messages and error-body shapes (the code is the source of truth; nothing new is invented); field, column, header and variable names; tables or things the card names that aren't in the code; validation order and edit rules; anything in the card that's unclear or incomplete. **The request and response structures (rule A28, D84):** every API the card names that it adds, changes or relies on needs its structure in the card's `## API request and response`. For each one missing, ask the user to paste the request and the response; never write one, derive it from the code or fill in a field. Save the answer, exactly as given, to `card.md` under `## API request and response` ("given by the user at pick-up") and record it (rule A27). Where the code differs from a structure, show it as a "Found" line; the user decides. **Also, when the card has a WS1 schema (rule A22, D85):** its keys are every key of the card's request and response structure, with their types (`null` = optional, e.g. `updated_at`, `updated_by`, `updated_by_name`); show every field the WS2 model or service has that the structure doesn't (and the other way round) as a "Found" line, and the user decides. When the WS1 schema needs a common block (pagination, the audit fields) and no shared schema helper gives it yet, ask where the helper goes and its name (D85); the plan names it. Ask the user about them **the grilling way** (`rulesets/grilling.md`, rule A26): first the facts you found in the code as "Found" lines, then the real decisions **in numbered rounds, each with a recommended answer** that "yes" accepts, and follow-up rounds until nothing is open. **No separate summary round here (D90):** the draft plan in step 9 lists every answer under `## Decided before planning`, and approving it in step 10 confirms them. Record each answer with `bash scripts/run.sh decide` (item 5) and write one pointer line per answer under `## Decided before planning` at the end of `runs/<KEY>/card.md`. **When continuing:** read `runs/<KEY>/card.md` first (its `## Explained at pick-up` and `## Decided before planning`) and `runs/<KEY>/decisions.md` (every decision in full) and ask only what isn't answered there, plus any new difference the newer code brings. If there's nothing to ask, say so and go on. Log the step; `set <KEY> step 9`.

**9. The draft plan.** Build it from these together: the ruleset (Step 7), the user's memory (re-read for the `plan` phase: `bash scripts/memory.sh for plan <repos>`; an entry may change a ruleset point, and the agent rules always win, A8), the card files (`card.md` with its `## Explained at pick-up` and `## Decided before planning`), the code, the ACs and the special cases (migrations and seeders: the existing pattern, D51; queues; setups). Show the plan **in chat**, in the ruleset's plan format (its Step 4):
   - `Ruleset: <the ruleset file of each repo> · Memory applied: M2 (changes: <the ruleset point it changes, if any>)` (or `none`); a web repo's part of the plan follows the frontend ruleset's plan format (its Step 4)
   - `## Summary` (the card in a few lines) · `## Acceptance criteria` (as in the card) · `## Decided before planning` (the answers from step 8, one line each with its decision number)
   - `## Changes`: one `###` part per repo, in the order to build it (WS2 before WS1, D26), each a numbered list of the files: what changes, where
   - `## AC → Implementation Mapping` (a table: AC · where · how)
   - `## Validation, reuse and response fields`: each request check and where it goes (rule A20: WS1 schema for presence, type and format; WS2 controller inline or a utils function for request-only business checks; WS2 service for database checks); the existing functions to reuse and where they are, and each new function with "searched, none found" (rule A21); the WS1 response fields as confirmed, required or optional (rule A22)
   - `## Error codes` (the existing ones used, from the code) · `## Migrations, seeders, queues` (or "none"; migrations and seeders are reviewed by the user and run only after a separate yes, every run, rule A23) · `## Tests` (what gets committed, the coverage gate) · `## Out of scope`
   - **A small card (D90)** is a **Bug** or a **Task** with **one repo**, **at most 4 ACs** (the card check's count; a Bug without ACs counts 0) and **no migration or seeder** in its plan. Its plan is short: under the `Ruleset:` line, `Size: small card (<type>, 1 repo, <n> ACs, no migrations or seeders)`; then `## Summary`, `## Decided before planning`, `## Changes`, `## AC → Implementation Mapping`, `## Validation, reuse and response fields`, `## Error codes` and `## Tests`, each kept to what it needs (one line when there's nothing); the ACs aren't copied (they're in `card.md`); `## Migrations, seeders, queues` says "none" and `## Out of scope` is one line. Every other card gets the full plan above, with `Size: full plan (<why, e.g. 2 repos>)` under the `Ruleset:` line. The approval in step 10 is the same for both.
   Nothing is saved yet. Log the step; `set <KEY> step 10`.

**10. ✋ Manual approval (rule A18), strictly necessary.** Ask the user to approve the plan. On changes, change it and show it again, until they say yes in so many words. Nothing is written to the run folder and nothing is pushed before that. Log the step.

**11. Save and finish.** Write the approved plan to `runs/<KEY>/plan.md` with your file-writing tool (the shape above, `# <KEY> — plan` as its title, "Approved by the user on <date>" under it). Then `bash scripts/run.sh set <KEY> size small` (or `full`; the `Size:` line of the plan), `set <KEY> phase develop`, `set <KEY> step 1`, `set <KEY> next "/flow-develop <KEY>"`, log "plan approved and saved", and `bash scripts/run.sh save <KEY> "plan approved"`. Show the save's output and end with one line: `Done: <KEY> is planned. Next: /flow-develop <KEY> (Codex: $flow-develop <KEY>), or say "develop <KEY>".`

## Before a long step, say how long (D74)

Before you start each step below, say its line in one sentence, so the user knows what's happening and roughly for how long. The times come from real runs; "several minutes" where none was timed yet. Plain words (rule A25).

- Step 7: "⏳ Bringing the latest code into the card's branches and reading it: about 5 minutes for 2 repos."

## Rules
- Every step writes its history line with the rules and memory applied (A1, A17). Pausing is just stopping; the next `/flow-start <KEY>` carries on.
- The card in Jira: only its sprint, its status and its assignee change (D58); never Blocked (A3).
- Branch names follow the strict rule (A12); cloning is manual (D53); folder access is asked first (A15); nothing runs in a repo here except `card-branch.sh`.
- The code is read before the plan (with the latest base branch brought in first), every difference is asked about first, and the plan is saved only after the user's manual approval (A16, A18).
- Fewer rounds, never fewer checks (D90): the card's gaps and the repos are one round; the plan approval confirms the answers of step 8; a small card gets a shorter plan with the same approval. The card check, the code-first questions and the approval itself are never skipped.
- The ruleset (`rulesets/`) is read, never changed (A19). The user changes its points only through their memory, and the plan says which entry changed which point.
- Never read, print or store secrets, `.env` values or Keychain values (A6). The run folder never holds them.
- Run the scripts exactly as written here (`bash scripts/…` from the closio-agent folder, no `cd`, nothing joined with `&&`). They're pre-approved in Claude Code and Codex, as are the Jira reads and the two Jira changes (D57).
- **The Jira API backup (D88, rule A31).** The Jira connector comes first. If its tools still aren't there after 3 tries (`bash scripts/wait-seconds.sh 10` between them), or a Jira tool fails or can't do what's needed, switch to the API by yourself, without asking: say once `Jira connector not available: using the Jira API backup.` and use `bash scripts/jira-api.sh` for the rest of this command: `get <KEY>` (step 2), then in step 3 `sprint <KEY>`, `move <KEY> "In Development"` and `assign <KEY>`. Text it posts is first written with your file-writing tool to `local/jira/<KEY>-<what>.md` (private, never pushed), unless the step names a file. Before you redo a change that failed through the connector, read the card again (`get`, `comments`), so nothing is done twice. Every yes stop stays exactly as with the connector. Exit code 3 means the backup isn't set up either: show `❌ Jira isn't connected in <Claude Code or Codex>` with the connector's fix (as in `/flow-doctor`) and `Or set up the Jira API backup: /flow-configure-user jira-email, then /flow-configure-user jira-api-token`, and stop.
