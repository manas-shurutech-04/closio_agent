# Changelog

Dated list of what changed in closio-agent. Newest first.

## 2026-10-24

- **closio-agent's tests in about 25 seconds** ([D93](design-decisions.md#d93), build rule R20 and rule 29 in `AGENTS.md`): `bash tests/run.sh --docker --coverage` runs every test in a Linux container with the Mac's bash 3.2, instead of about 11 minutes on the Mac (its security software checks every program the tests start). It's now the check before a commit. Start Docker Desktop first; the first run builds the test image (about 90 MB, once). Without Docker Desktop, `bash tests/run.sh --coverage` still runs the same tests on the Mac. Every test now runs as a job of its own, so a file with slow tests no longer holds up the end.
- **Four fixes the new tests found** ([D92](design-decisions.md#d92)):
  - `ship.sh`: a push GitLab's own rules decline (a protected branch, a push rule, a server hook) now says so, with GitLab's reason, instead of "someone else pushed".
  - `card-branch.sh`: the "to undo the rebase" tip now shows at every rebase conflict, the first one too.
  - `gitlab-mr.sh comments`: an answer that isn't a list (e.g. a proxy's error page) now stops at once with one ❌ and its fix, instead of asking for 20 pages and printing about 40 error lines.
  - `setup-repo.sh run all`: a BullMQ repo after a repo that set up Redis now still gets its Redis memory-setting check (once per run).

## 2026-10-23

- **closio-agent's own tests** ([D92](design-decisions.md#d92), build rule R20, new rule 29 in `AGENTS.md`): 671 tests, covering 99.7% of the scripts' lines. `bash tests/run.sh` checks closio-agent's scripts, commands and rules against fakes: no AI, no real Jira, GitLab, VPN or Keychain, nothing to install. `bash tests/run.sh --coverage` also shows the share of the scripts' lines the tests ran, and fails under 90%. Every script change now comes with its tests. How to run them: [setup guide](setup-guide.md#test-closio-agent-itself).
- **One call after every step of a card command** ([D91](design-decisions.md#d91), rule A17 / `AGENTS.md` rule 12 reworded). The AI reads `AGENTS.md` and `docs/agent-rules.md` in full when a card command starts, and again only when one of them changed or the conversation was summarized. After every step, one call (`bash scripts/run.sh step …`) writes the history line, moves to the next step, checks the rules files and prints your memory for the next step. When a rules file changed, the AI says so in one line, reads it again and goes on, and the card's history gets one line saying from where. Old history lines are never rewritten.
  - **Codex:** the hook file changed, so approve the hooks again in `/hooks`, including the new one under "After context compaction".
- **Faster card work, with the same checks** ([D90](design-decisions.md#d90)), from a testing agent's suggestions and your answers:
  - `/flow-start` asks about the card's gaps and the repos in one round; at planning the draft plan lists your answers and approving it confirms them (no extra summary round).
  - **A small card** (a Bug or a Task with one repo, at most 4 ACs, no migration or seeder) gets a shorter plan, with the same approval, and `/flow-verify` uses the quick check for it unless you type `full`.
  - `/flow-verify` starts the servers in the background while it reads and leaves them running for a re-run (reused only while the code is the same; `/flow-push` stops them). A one-repo backend card's quick check skips the live call only for a scenario that a committed API test already checks without faking what it depends on.
  - Fewer prompts: a repo's git is read with the new `scripts/repo-git.sh` (read-only, never a `.env` file), pre-approved in both tools; Claude Code also allows `git log`, `git diff`, `git status` and `git show`, never on a `.env` file. The card rules get a rule 2 about it.
  - Not taken: sub-agents for heavy reading, and the deployment doc drafted early. The one-call-per-step suggestion came next, as D91 (above).
- **For the closio-agent builder only: a doc-check hook** ([D89](design-decisions.md#d89), new rule 28 in `AGENTS.md`). At the end of a reply, `scripts/build-sweep-hook.sh` checks which docs, rule files and build-memory files a change to closio-agent still needs, and has the AI make them in the same reply. It runs only on the builder's Mac and never in a card session: on any other Mac it does nothing. In Codex it shows in `/hooks` next to the card hooks; teammates don't need to approve it.
- **The Jira API as a backup** ([D88](design-decisions.md#d88), new rule 27 in `AGENTS.md`). The commands use Jira through its connector first. When the connector's tools still aren't there after 3 tries, or a Jira tool fails, they switch by themselves to Jira's REST API and say so in one line ("Jira connector not available: using the Jira API backup."), then do the same there: read a card and its comments, move it (never to Blocked), set its sprint and assignee, post or edit a comment, create a card. Every yes stop stays. New script `scripts/jira-api.sh`; the card and its comments come back as Markdown, like the connector's.
  - **Set it up (optional):** make an Atlassian API token ([setup guide, section 3.1](setup-guide.md#31-the-jira-api-backup-optional)), then `/flow-configure-user jira-email` and `/flow-configure-user jira-api-token`. Without it, a missing connector stops the command with both fixes.
  - `/flow-doctor` has a new section, "Jira API backup": ✅ when it works, ⚠️ when it isn't set up (never ❌). When the connector is missing but the backup works, the Jira line is a ⚠️, not a ❌.
- **Clearer words: the card's folder is pushed to GitHub automatically** after every reply while you work on a card (the change below, [D87](design-decisions.md#d87)); `README.md`, `docs/README.md`, `docs/commands.md`, `docs/user-guide.md`, `docs/agent-rules.md` and `AGENTS.md` now say so in those words.
- **The card's folder is saved to GitHub after every reply** ([D87](design-decisions.md#d87), new rule 26 in `AGENTS.md`). While you work on a card, the card's saved copy (branch `runs/SCRUM-567`) is committed and pushed at the end of every reply whenever the folder changed: "SCRUM-567: auto-saved after /flow-develop" (or "after a reply"). Nobody has to push it by hand, and a teammate sees every step and decision at once. Only that branch; never `main` or a code repo; never forced. A failed push shows one warning with its fix and is tried again after your next reply.
  - **Codex:** the hook file changed, so approve the hooks again in `/hooks` (both: "When the user submits a prompt" and "Right before Codex ends its turn"). `/flow-doctor`'s section is now "Card hooks" and shows the steps.
- **The card rules, at every prompt about a card** ([D86](design-decisions.md#d86), new rule 25 in `AGENTS.md`). A hook adds [`rulesets/card-rules.md`](../rulesets/card-rules.md) to every card command, every prompt that names a card key (for example "develop SCRUM-567"), and every later prompt in that session, in Claude Code and Codex. **Its first rule:** every decision on the card is written to the card's `decisions.md` the moment it's confirmed, and checked before the AI ends its reply. More rules can be added to the same file.
  - **Codex:** trust the hook once (`.codex/hooks.json`); until then Codex skips it. The steps: start Codex in the closio-agent folder, type `/hooks`, approve the hook under "When the user submits a prompt", then send any prompt that names a card. `/flow-doctor` shows these steps as a ⚠️ until Codex has run the hook.
  - `/flow-doctor` has a new section, "Card rules hook", that tests it and checks it's set in both tools.

## 2026-10-21

- **Two review and build rules** ([D85](design-decisions.md#d85)), for backend cards:
  - **The WS1 schema holds every key of the card's request and response structure**, with its type: the body, the query and each response. A missing key or a wrong type is a must fix in `/flow-review`; a key the card doesn't have is shown to you. Rule A22 (`AGENTS.md` rule 17) now takes the keys from the card's structure, not from what the WS2 response can return.
  - **Schema blocks are shared:** a block a shared helper already gives is reused; pagination and the audit fields come from a shared helper in every new schema (where the first one goes is asked while planning). The schemas that still copy them are moved through a separate card.
  - **Better queries:** one list in the backend ruleset (one query instead of several, only the columns needed, filtering and counting in the database, indexes, transactions). `/flow-develop` writes new queries by it and says why for each one in its summary; `/flow-review` suggests a better query with a "Why" line, from the code only.
  - Request input in raw SQL is no longer checked in the review (your decision).

- **Request and response structures now come only from you** ([D84](design-decisions.md#d84), new rule 24 in `AGENTS.md`). The AI never writes one, never takes one from the code and never fills a gap: if one is missing, it asks you.
  - **The card template** has a new section, `## API request and response`, right after Context: each API's request and response, exactly as you give them. Backend cards: every API the card adds or changes. Web cards: every API the card relies on.
  - **`/flow-check-card`** and the pick-up show ❌ when a card names an API but has no structure for it. **Older cards that name an API now stop at pick-up until you paste the structures.**
  - **`/flow-start`** asks you to paste any missing structure and saves it with the card. **`/flow-develop`** builds to it, and the tests and mocks use it.
  - **`/flow-verify`**, both ways, makes one success call per API in the card's section and compares the answer with the structure you gave (new `scripts/response-shape.sh`): each missing, extra or wrongly typed field is listed, and you decide.
  - The three example cards are waiting for their real structures from you, so they show the new ❌ until then.

- **`/flow-push` checks every AC again after a rebase that brought new code** ([D83](design-decisions.md#d83)). Before, after the rebase only each repo's unit tests and lint ran before the commits, so a conflict resolved by hand, or newer code from the base branch, wasn't AC-checked until dev, after the merge. Now:
  - The rebase says what came in for each repo: "3 newer commit(s) from develop came in" or "nothing new on develop".
  - **When a repo had a conflict or newer commits came in**, a new step 6 checks every AC again **the quick way** (as `/flow-verify`'s quick check does it, whichever way the card was checked before), before any commit. Test data and calls that write still wait for your yes. No story check. The result is a new run in the card's `verify.md`.
  - When nothing came in and there was no conflict, one line says the earlier checks still hold.
  - **A failure stops the push before any commit** (the tests, the ACs, or a commit hook). It's written as a failed run in `verify.md`, and **`/flow-develop` now takes the card back** from the push step (before, it refused, so its suggestion led nowhere). Then `/flow-verify` and `/flow-push` again.
  - `/flow-push`'s steps 6–11 are now 7–12.

## 2026-10-19

- **New: `/flow-qa`** ([D81](design-decisions.md#d81)), for a finished card that QA is testing. It reads QA's new comments on the Jira card, checks each one against the card's ACs, its decisions, the deployment doc, the merged code and the dev environment, and drafts the answer: one reply per round, each point quoted, posted as you after your yes. A real bug becomes a separate Bug card (drafted for you; created in To Do, unassigned, linked to the story, only after your yes), worked with `/flow-start` like any card. The story moves only from Blocked to In Development (when you approve a Bug card) and back to Ready for Test once its Bug cards are done (from `/flow-qa`, or `/flow-finish` on the last Bug card), each after your yes. `/flow-qa SCRUM-567 check` only lists QA's new comments.
- **The web app has its own ruleset** ([D80](design-decisions.md#d80)): `rulesets/frontend-story-workflow.md`, written from the web app's `development` branch. It says how a web card is planned and built the way the app already does it: where files go, the shared components and helpers to reuse (never re-create), how a screen calls the backend and shows errors, the Vitest test patterns, test ids for new screens, and the app's known problems not to copy. `/flow-start`, `/flow-develop`, `/flow-review` and the others now read it for the web app instead of the backend ruleset's "common practices"; `/flow-doctor` checks both rulesets are there.
- **The build chat transcript is no longer in the repository** ([D79](design-decisions.md#d79)): it stays on the builder's Mac only, and it was erased from the git history, so every commit id changed. If you cloned closio-agent before 2026-10-19, clone it again (or reset to the new `main`).
- **New: `/flow-review`** ([D78](design-decisions.md#d78)), for a pushed card while its merge requests wait for the merge. It shows each MR's state (who approved, conflicts, the pipeline and any failed job); reviews the card's code itself first: the story (every AC covered by code and tests) and the basics (no function written again that already exists, each piece in the right file, no unused or debug code, no hard-coded values, tests for the new branches), plus the tool's own reviewer, with the findings in chat only; then the reviewers' new comments: a drafted reply for a question, a tested fix and a reply for a change request, your call for the rest. After your yes, the fixes go into the same MR as new commits (never forced, no rebase: the one exception to "one push") and the replies are posted as you. It never resolves a thread or moves the Jira card. At most 3 self-review rounds per run and 2 tries per failing fix, so it never loops. `/flow-review SCRUM-567 check` only lists what's new. New script actions: `gitlab-mr.sh comments | reply | pipeline`, `ship.sh push-update`, `repo-run.sh review`; the checklist is `rulesets/code-review.md`.
- **Every decision on a card is written down in one place** ([D77](design-decisions.md#d77), new rule 23 in `AGENTS.md`): each card's folder gets `decisions.md`, one numbered row per decision, from pick-up to Ready for Test: your answers, your approvals and refusals at the safety stops, a memory entry that answered for you, a change you asked for in the middle of a command; when, at which step, and who decided. The card's other files (`card.md`, `develop.md`, `verify.md`, `ship.md`) keep only a one-line pointer ("decision 3"). New: `bash scripts/run.sh decide`. Cards started earlier (SCRUM-540, SCRUM-523) are left as they are.
- **Decisions during a card are asked the "grilling" way** ([D76](design-decisions.md#d76), new rule 22 in `AGENTS.md`): while `/flow-start`, `/flow-develop`, `/flow-verify`, `/flow-ac-check`, `/flow-push` or `/flow-finish` runs, every question, and every change you ask for in the middle, is handled like this: what the agent can find (the card, its folder, the code) is shown as "Found" lines and never asked; only real decisions are asked, numbered, in rounds, each with a recommended answer ("yes" accepts it, "yes to all" the round); follow-ups until nothing is open; then what you agreed, and nothing changes before you confirm. The decisions are saved in the card's folder. The safety stops (migrations, test data, the commits, the push, Jira moves) still ask their own yes or no. The method is in `rulesets/grilling.md`, adapted from Matt Pocock's "grill me" (MIT licence, kept in the file).
- **New: `/flow-grill`** (under "Any time" in `/flow-help`): `/flow-grill "<your plan or idea>"` or `/flow-grill SCRUM-567` grills it with you the same way; it only reads, and a card you've picked up gets the agreed answers in its `card.md`.

## 2026-10-18

Per repo it brings your branch up to the latest base branch (your work put aside, the branch rebased, your work put back; a conflict waits for you), runs the tests again, proposes the atomic commits (each layer's code with its tests, `SCRUM-<n>: …` messages) for your approval and makes them (the repos' git hooks always run), then, after your yes, pushes once per repo: the push creates the merge request, titled `SCRUM-<n>: <card title>`, ready for review and assigned to you, and a script sets its description (the Jira link, the migrations and seeders to run) and reviewers through the GitLab API.
