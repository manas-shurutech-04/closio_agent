# Agent Rules

Every rule closio-agent follows when it runs, in one place. **Every rule is strict.** Each one links to the decision that explains why, and says where it's applied today.

- **Git rules (G1–G4):** how the agent uses git.
- **Behaviour rules (A1–A25):** everything else.
- **`AGENTS.md` column:** the rules the AI must follow in every session are also written in [`AGENTS.md`](../AGENTS.md), which Claude Code and Codex read at the start of every session ([D45](design-decisions.md#d45)). The number is the rule's number there.
- **Your user memory never overrides these rules** (A8). If one of your memory entries disagrees with a rule, the agent tells you and follows the rule.
- The rules for **building** closio-agent (R1–R18) are a different list, in [build-memory/rules.md](../build-memory/rules.md).

> Status (2026-10-18): the setup commands are built (incl. `flow-setup-repo`, `flow-memory`, `flow-check-card`, `flow-help`), and of the card phases the pick-up, the plan, the development, the checks, the push and the after-merge step (`flow-start`, `flow-develop`, `flow-verify`, `flow-ac-check`, `flow-push`, `flow-finish`, `flow-status`): every phase is built. "Not built yet" below means the rule is decided and will be applied by that phase.

## Git rules

| # | Rule | Why | `AGENTS.md` | Where it's applied today |
|---|---|---|---|---|
| G1 | Always pull from the base branch set for the repo (`base_branch` in `config/repos/<repo>.yaml`; it can differ per repo). | [D51](design-decisions.md#d51) | — | Built (C2): `scripts/card-branch.sh` pulls the repo's base branch before creating the card's branch (`flow-start`). `card-branch.sh update` brings the latest base branch into the card's branch before every plan (step 7); `card-branch.sh rebase` rebases onto the latest base branch before the commits (C5, `flow-push`) |
| G2 | Before every push, rebase the branch onto that base branch, in this order: **stash the changes → rebase → stash pop → then atomic commits**. | [D10](design-decisions.md#d10) | — | Built (C5): `flow-push` step 4, `scripts/card-branch.sh rebase` / `rebase-continue` (a conflict waits for the user) |
| G3 | Develop together first, then make atomic commits. Never push everything as one commit. | [D10](design-decisions.md#d10) | — | Built (C3): `flow-develop` develops together and never commits; built (C5): `flow-push` proposes the atomic commits, the user approves them, `scripts/ship.sh commit` makes them |
| G4 | Only **one push** to the remote, after connecting to GitLab. | [D10](design-decisions.md#d10), [D18](design-decisions.md#d18) (tests run before the push, so a failure never needs a second push), [D31](design-decisions.md#d31) (the same push creates the MR) | — | Built (C5): `flow-push` pushes once per repo, after the user's explicit yes, never forced (`scripts/ship.sh push`) |

## When a rule changes

In the same step:

1. record the decision in [design-decisions.md](design-decisions.md);
2. update this file;
3. update `AGENTS.md` if it's a rule the AI must follow in every session;
4. update the build memory's copy (`build-memory/project-context.md`, sections "Agent Git Rules" and "Agent Behaviour Rules"), which also keeps who asked for it and when.
